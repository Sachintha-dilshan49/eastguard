# Deviations from the specification

Each entry records a deliberate simplification, why it was made, and what would remove it.

## Task 3 — TLS and identity

| # | Spec | Simplification | Reason / removal |
|---|------|----------------|------------------|
| 3.1 | §9.1 "protected paths for PKCS#12 files … RPC credentials" | All runtime TLS stores (token service, gateway, control plane, workloads, trust store) share one demo password (`EASTGUARD_STORE_PASS` / `keys\store.pass`). The lease signer and the CA stores have their own passwords. | One password per process role is the production setup. The demo runs every role on one machine as one user. Remove it by adding per-role `*.passwordEnv`/`*.passwordFile` settings (the config keys already exist per component). |
| 3.2 | §9.1 "Do not put secrets in … command-line arguments" | Followed. keytool reads passwords with `-storepass:env`. When no env var is set, the password lives in a git-ignored file with a current-user-only ACL. | — |
| 3.3 | §4.1 certificate revocation | No CRL/OCSP. A revoked certificate is expressed as a leaf fingerprint in `Workload.revokedCertificates` in the enforcement snapshot, and `WorkloadIdentity`/`PolicyEvaluator` check it on every connection. | Matches the spec's snapshot-based revocation; PKIX revocation checking would need a CRL distribution point the demo CA does not run. |
| 3.4 | §4.1 session resumption | TLS session resumption is left on. The identity, revocation and validity checks run on every connection against the current state, including resumed sessions, so resumption cannot bypass them. | — |
| 3.5 | `ReasonCode` | Appended `BAD_IDENTITY(18)` for "no single approved workload URI SAN / certificate outside validity", distinct from `IDENTITY_DISABLED`. | Append-only, as the enum's wire contract allows. |

## Task 4 — Token service and client

| # | Spec | Simplification | Reason / removal |
|---|------|----------------|------------------|
| 4.1 | §6.2 freshness, §9.1 "load policy from the control-plane journal" | The token service runs on a **static bootstrap snapshot** read from `bootstrap.*` keys in its properties file, and treats it as always fresh. | No control plane exists yet. Task 6 replaces the `Supplier<EnforcementView>` passed to `TokenServer` with a synced view that becomes unusable after `state.maxAgeMillis`. |
| 4.2 | §4.2 "per-client limits" | Fixed one-second window per authenticated identity (`IssueLimiter`), default 20 requests/s. The map is capped at 10 000 identities and fails closed when full. | Good enough to stop a single workload from hammering the signer. A token bucket would smooth bursts. |
| 4.3 | §1 "selected token-service denials" telemetry | Not emitted yet. Denials are logged (identity, service, reason, never the token) and counted in `TokenServer.Stats`. | **Resolved in Task 7:** `TokenServer.reportTo` sends POLICY_DENY (known service) and QUARANTINED denials for TLS-authenticated peers. |
| 4.4 | §4.1 / §10 "Untrusted certificate … TLS fails" | Met on the server side, which is the authoritative signal. With TLS 1.3 the **client** finishes its handshake before the server rejects its certificate, so the client sees the failure on its first read: as an `SSLException`, or on Windows often as a `SocketException` (connection reset) because the reset discards the server's alert. The demo and tests assert the server-side handshake failure and that no application reply was sent. | Inherent to TLS 1.3 client authentication. |

## Task 5 — NIO gateway

| # | Spec | Simplification | Reason / removal |
|---|------|----------------|------------------|
| 5.1 | §6.2 freshness, §9.1 "load policy from the control-plane journal" | The gateway uses the **same static bootstrap snapshot** as the token service: `bootstrap.file` in the gateway config points at the token service's properties file, and the view is always fresh. The gateway already re-reads its `Supplier<EnforcementView>` at AUTHORIZE, on `finishConnect()`, and in a 50 ms sweep that closes indexed sessions when the view stops being usable. | Task 6 passes a synced view, calls `reevaluate()` after installing a snapshot, and `closeAll(NOT_READY)` when freshness expires. |
| 5.2 | §1 "emit authenticated UDP events for gateway decisions" | Decisions go to a `DecisionSink`. Only `CountingDecisionSink` (non-blocking counters) exists. | **Resolved in Task 7:** `DecisionSink.udp(TelemetrySender)` when `telemetry.collector` is configured. |
| 5.3 | §4.3 deadlines | Deadlines are checked by a sweep every 50 ms over all connections (O(n), about 1,000 entries), so a timeout fires up to 50 ms late. The queued-bytes gauge in `Stats` is sampled by the same sweep. | A timer wheel would give exact deadlines; not needed at these timeouts. |
| 5.4 | §4.3 "total buffer budget" | Each connection **reserves a fixed cost** at accept: two one-record TLS buffers, plus a plaintext buffer per direction (`limits.relayBufferBytes`, at least one TLS record), about 96 KiB with the defaults. A connection is rejected when the reservation would exceed `limits.bufferBudgetBytes`. Memory is bounded by construction rather than by tracking live usage. Water marks apply to the plaintext queue in each direction (client→backend: unwrapped bytes waiting for the backend; backend→client: backend bytes plus ciphertext waiting for the client). | Reserving up front means a connection admitted under the budget can never fail later for lack of memory. Lazy or pooled buffers could raise density. |
| 5.5 | §4.3 "handshake concurrency" | `limits.maxHandshakes` counts connections in TLS_HANDSHAKE or READ_PREAMBLE. At the limit the gateway **stops accepting** (removes `OP_ACCEPT`) and new connections wait in the kernel backlog. Global and per-peer connection limits and the buffer budget **reject** (accept, then close). | Pausing accept for short-lived handshake pressure keeps legitimate clients working; hard limits still reject excess. |
| 5.6 | §4.2 step 5 "never forward early client data before admission" | The gateway reads no client bytes between a complete preamble and the flushed reply. Plaintext that arrived **in the same read as the preamble** is a protocol violation: the connection is closed with no reply and nothing reaches the backend. Bytes a client sends later while waiting (non-conforming) are read only after `ALLOW` and then relayed. | A conforming client waits for the reply (§5.1). |
| 5.7 | §5.1 replies | A malformed preamble (bad magic or version, token length outside 1..2048, trailing data) is closed **without a reply**, as the token service does for malformed requests. It is recorded as DENY/`INVALID_TOKEN`, attributed to the TLS identity when the certificate maps to a workload. A token that frames correctly but does not parse or verify gets a DENY reply. | — |
| 5.8 | §4.2 step 6, §10 "quarantine during pending backend connect" | A session closed by a command (quarantine, revocation, stale state) **while its backend connect is pending** is denied: the backend leg is cancelled, the client gets the matching status (e.g. `QUARANTINED`), and no ALLOW is sent. A **live** session is cut on both legs at once, with no reply and queued payload discarded. | — |
| 5.9 | §8 adapters, §10 "backend becomes slow" | `BackendConnector` is an adapter for the non-blocking backend connect. Tests use a double that starts `connect()` late or never, to simulate a slow network. On Windows a loopback connect to a closed port, or to a listener with a full backlog, is refused at once, so no real loopback fixture can hold a connect pending. | Production uses `BackendConnector.DIRECT`. |
| 5.10 | §9.3 "on gateway shutdown, drain only allowed sessions for a bounded interval" | `NioGateway.close()` stops accepting and **cancels all connections immediately**. | Add a draining phase (stop admissions, wait up to N seconds for RELAY sessions, then close) when an operational shutdown procedure is needed. |
| 5.11 | §4.3 "do not operate on an engine concurrently" | All delegated tasks (handshake and, rarely, data phase) run on the bounded `limits.tlsTaskThreads` executor. While a task runs, the connection has no interest ops and the selector does not touch its engine. A connection closed meanwhile is closed **without touching the engine** (no `close_notify`). If the task queue is full, the connection is closed. | — |
| 5.12 | §10 "Admission p95 under 5 ms on a warmed gateway" | `DemoM1_Nio` reports two numbers, measured by the gateway from complete preamble to flushed ALLOW. **Burst** (500 connects, 64 at a time, client crypto in the same JVM): p95 about 120 ms, mostly queueing behind other handshakes on the selector. **Warmed, sequential**: p95 about 1.1 ms on the development laptop. Neither is a load test on declared hardware. | Spec §10 load tests remain to be done (Task 10). |
| 5.13 | §6.1 decoys | One decoy listener per gateway (`decoy.listen`), served by the gateway's selector thread with no thread of its own. Accepts are bounded per wake-up, and there is no per-source rate limit on DECOY events beyond that. | The sink must drop rather than block; the Task 7 UDP queue is bounded. |

## Task 6 — Control plane

| # | Spec | Simplification | Reason / removal |
|---|------|----------------|------------------|
| 6.1 | §8 "single writer" | The single writer is **one lock** around authenticate → validate → journal append + force → publish, not a dedicated writer thread. Reads (`sync`, dashboard) use the published immutable snapshot without the lock. | Same serialisation guarantee with less code. |
| 6.2 | §7.2 audit "outcome" | Only **committed** mutations are journaled and audited, with `outcome=COMMITTED`. Rejected requests (INVALID, CONFLICT, UNAUTHORIZED) are logged (no credentials) but neither journaled nor remembered for idempotency, so the same request ID can be retried after a rejection. | Rejections do not change state. A durable audit of rejections would add a second, non-enforcement record type. |
| 6.3 | §7.1 idempotency | The idempotency map (principal + request ID → digest, revision) is rebuilt from the journal at startup and grows by one entry per committed request. It has no retention limit. | Mutations are operator-scale. Bound it with a retention window once journal compaction exists. |
| 6.4 | §6.3 watermark retention | Release and expiry watermarks are **never pruned**: one entry per selector ever released, kept in the snapshot and across restarts. | Tiny. Prune after "max staleness + max lease + skew" (2 min) once a pruning transition is added. |
| 6.5 | §7.2 journal | Every mutation record is replayed from the start. There are no snapshots or compaction. A corrupt complete record or a revision gap stops the control plane from starting (`NOT READY`). An incomplete trailing frame is truncated automatically and logged as a WARNING; that frame was never acknowledged because acknowledgement follows `force`. Recovery from corruption is manual: restore a verified backup or fence and re-bootstrap. | Startup time is fine at demo scale. Backup/restore drills belong to Task 10. |
| 6.6 | §7.1 "TLS client principal" | **One RMI client TLS identity per process**: the first context passed to `RmiSupport.installClient` is used for every RMI connection from that JVM. In single-JVM demos and tests, all clients share it. Each call's API credential identifies the principal and is checked for role on every call. | RMI pools connections per endpoint across callers, so a TLS identity cannot be per-caller anyway; the spec asks for credentials on every call for this reason. |
| 6.7 | §7.1 deserialization | Server-side call arguments pass a per-object allowlist (request DTOs plus `Selector`, `Edge`, `IpAddress`, `Bytes`, enums, immutable lists) with depth/reference/array/byte limits. Client processes install a process-wide filter that also allows the response DTOs, the control-plane stub (proxy + our socket factory) and JDK `java.lang`/`java.io`/`java.rmi` exception types (how RMI reports remote failures). The registry and DGC keep the JDK's built-in filters. The snapshot travels as `SnapshotCodec` bytes, never as an object graph. | — |
| 6.8 | §7.1 "server endpoint verification" | Clients connect only to numeric `host:port` pairs on their configured allowlist (registry and object port). A stub advertising anything else is refused before connecting, and the server certificate must carry that IP as a SAN. | — |
| 6.9 | §7.1 credentials | High-entropy (32 random bytes) per-principal secrets, stored by the control plane as plain SHA-256 digests (no KDF; they are not passwords) and compared in constant time. `scripts/gen-credentials.ps1` provisions, rotates (`-Rotate`/`-Retire`, two digests during overlap) and revokes (`-Revoke`). The control plane reloads the file when its timestamp changes. | A rotation needs file access on the control-plane host; an RMI API for it would be a later admin feature. |
| 6.10 | §7.1 ops | `recordObservations` and `proposeAction` (detector) and `freezeBaseline` (admin) authorize the caller, then return `UNAVAILABLE` "not implemented yet". | `recordObservations` and `proposeAction` **resolved in Task 7**; `freezeBaseline` remains for Task 9. |
| 6.11 | §6.2 step 3 | `StateSync` polls every `state.pollMillis` (default 1 s, ±20 % jitter). It does not yet track the newest revision from verified multicast notices or a quarantine overlay (`EnforcementView.newestKnownRevision` = installed revision, empty overlay). `syncSoon()` exists for the "sync now on a newer notice" path. Quarantine therefore reaches a gateway within about one poll interval (DemoM5: ~1 s). | Task 8 adds notices, overlays and the catch-up pause. |
| 6.12 | §6.2 step 4 | Freshness is measured with the JVM's monotonic clock from the start of the last successful sync. After it expires, the gateway's 50 ms sweep ends every indexed session through `SessionIndex` (pending: status `UNAVAILABLE`; live: closed). The token service answers `UNAVAILABLE`. | — |
| 6.13 | §9.1 bootstrap | The bootstrap command reads the same `bootstrap.*` file format as before (`config/bootstrap.properties.example`) and writes it as revision 1 of an **empty** journal under the journal lock (refused if the journal holds state or a control plane is running). The control plane refuses to serve an empty journal. `DemoM1_Nio` and `DemoM2_Tls` still read that file directly as a fixed fixture, without a control plane. | — |
| 6.14 | §4.1 signer check | The token service no longer checks its signing key against a static published key at startup. Instead it issues only while the **synced** snapshot publishes exactly its public key under `lease.keyId` (otherwise `NOT_READY`). | The published keys now arrive with sync. |
| 6.15 | §7.3 "dashboard client certificate" | No separate console/dashboard certificate yet. RMI admin clients in the demo use the process's component certificate. | Add a `console` certificate to `gen-certs.ps1` with the dashboard (Task 9). |
| 6.16 | §9.1 RMI limits | RMI transport limits are the JDK's system properties, set by `RmiSupport.configureJvm` before first use: 5 s client handshake/response timeouts, 30 s server read timeout, at most 64 server connection threads. Quarantine TTL is capped at 24 h by default (`quarantine.maxTtlSeconds`). Requests are bounded (8 selectors, 10 000 edges, 200-character reasons). | — |

## Task 7 — UDP telemetry, threat detector, learning observations

| # | Spec | Simplification | Reason / removal |
|---|------|----------------|------------------|
| 7.1 | §6.1 score table, "count each event only once per signal" | Each event maps to **at most one** per-event signal: POLICY_DENY (authenticated) +30, IP_MISMATCH (authenticated) +60, DECOY +100, else SECURITY_DENY +10 for INVALID_TOKEN, WRONG_AUDIENCE, IDENTITY_MISMATCH, QUARANTINED, REVOKED, LEASE_SUPERSEDED, IDENTITY_DISABLED, BAD_IDENTITY. A policy denial is not also a +10 "security-related denial". Not scored: ALLOW, EXPIRED, NOT_READY, BACKEND_UNAVAILABLE, THROTTLED. | The spec lists the signals but not their overlap; one signal per event keeps the fixture scores unambiguous (30 → 40 → 50 → 110). |
| 7.2 | §6.1 scan signal | Distinct endpoints are `(dstIp, dstPort)` of **scored gateway events** (denials and decoy hits) in the last 5 s; ALLOWs, unscored failures and issuer events never count. "+50 once while the condition holds" is one contribution, refreshed while more than 10 endpoints are seen and aging out 10 s after the condition last held. | Keeps healthy and pilot traffic out of the scan signal, as §6.1 requires. |
| 7.3 | §6.1 "after a detector restart, suppress automatic action until pre-restart datagrams have aged out" | The detector keeps no state across restarts, so it cannot tell a first start from a restart. It **always** suppresses proposals for `telemetry.acceptanceMillis` (30 s) after start. Alerts are still raised, marked `suppressed: restart guard`. Events whose time is outside the acceptance window (30 s old, 5 s in the future) are rejected, which bounds how long a captured datagram can be replayed into a fresh detector. | Persisting dedup state would remove the guard; not worth it at demo scale. `DemoM3_Udp` uses a 2 s window. |
| 7.4 | §6.1 "suspend automation when input quality is degraded" | Degraded means: in the last 10 s at least 5 sequence numbers from trusted producers are missing and they exceed 10 % of the expected events, **or** the actor table overflowed. Forged, malformed, out-of-scope and duplicate datagrams are counted but do not degrade input, so junk traffic cannot switch automation off. A full control-plane dispatch queue (256) drops the proposal and logs it. | Thresholds are fixed constants; make them configurable once measured false-positive data exists. |
| 7.5 | §3.1 `LearningDraft`, §7.2 "batch distinct learning candidates" | The control plane keeps the learning draft **in memory only** (bounded by `learning.maxCandidates`, 10 000), with its own version. It is not journaled, so a control-plane restart empties it; candidates come back from ongoing pilot traffic. Observation batches are idempotent through a bounded in-memory map of the last 1 024 request IDs. | The journal's strict one-revision-per-record rule would make every batch bump the enforcement revision, which §3.1 forbids. A separate draft journal (Task 9 or later) would make it durable. The draft is documented as possibly incomplete, as §3.2 allows. |
| 7.6 | §3.1 `Alert` | Only alerts whose proposal the control plane **committed** are recorded there: the alert (score, signals, evidence references) is part of the same `AUTO_QUARANTINE` / `AUTO_LEASE_REDUCTION` journal record and appears in `getDashboard().alerts()`. Alert-only, suppressed, ineligible and refused alerts stay in the detector's log and bounded in-memory history (`detector.maxAlerts`). Refused proposals are not journaled (as 6.2). | A dashboard feed of detector-only alerts belongs with the dashboard (Task 9). |
| 7.7 | §6.1 automation rules | Rules exist on both sides. The **detector** (`automation.*`, `cidr.*`, `detector.protectedIdentities`, per-selector-and-action cooldown) decides what to propose. The **control plane** (`automation.*` in `control.properties`) is authoritative: action type enabled, TTL ≤ `automation.maxActionTtlSeconds` (5 min), score ≥ 50 (reduction) or ≥ 100 (quarantine), identity known and not protected, IP inside `automation.eligibleCidrs` and outside `automation.excludedCidrs`, no existing quarantine/reduction for the selector (CONFLICT, "not extended"), and at most `automation.maxActionsPerHour` (20) committed actions per rolling hour across all selectors (UNAVAILABLE). Both default to alert-only. | Two config files must agree to enable automation; the control plane's check is the one that matters. |
| 7.8 | §6.1 lease reduction | A lease reduction is a committed `LeaseReduction` (selector, `lease.stepUpSeconds` = 10 s, expiry ≤ 5 min). It caps **newly issued** leases only. It expires as a committed `EXPIRE_LEASE_REDUCTION` transition from the same 1 s `expireDue` sweep as quarantine TTLs. | — |
| 7.9 | §5.3 sequence numbers | The producer assigns `seq` when an event is **offered**, including events then dropped by a full queue, so local drops show up as gaps at the detector. With concurrent producers (token-service virtual threads) the queue order can differ slightly from `seq`, which the 1 024-entry window tolerates. | — |
| 7.10 | §5.3 producer scope, §6.1 issuer events | Inventory rules: a GATEWAY reports ALLOW (with identity) and DENY only for its own service on its own listener, and DECOY (without identity) only on its own decoy listener. The ISSUER reports only DENY with POLICY_DENY or QUARANTINED, with identity, on its own listener; its `service` is the requested service (`*` in the inventory). The token service reports a policy denial only for a service in the installed snapshot. One endpoint can belong to one producer only. | — |
| 7.11 | §5.3 dedup retention | At most `telemetry.maxBootsPerProducer` (8) live boot IDs per producer. The least recently seen boot is evicted only once it has been quiet for the acceptance window; until then a ninth boot is refused (`BOOT_LIMIT`, fail closed). | A producer restarting more than 8 times in 30 s is itself an incident. |
| 7.12 | §9.3 "rotate telemetry secrets per producer" | One key ID per producer in the inventory. Rotation is: new key file (`gen-credentials.ps1 -TelemetryKeys -Force`), new `keyId` in both configs, restart producer and detector. There is no overlap window with two valid keys. | Add a list of accepted key IDs per producer for hitless rotation. |
| 7.13 | §5.3 event time | The acceptance window relies on synchronized host clocks (±5 s future skew, 30 s age). | §9.1 already requires time synchronization. |
| 7.14 | §11 `DemoM3_Udp` | The demo runs the control plane in the same JVM and the detector calls it through `DetectorControl.direct` (credential and role still checked). The same calls over secured RMI, through the real deserialization filter, are covered by `RmiTest.testDetectorCallsOverRmi`. Keys and credentials are generated in memory. | Keeps the M3 demo independent of `keys\`; `ThreatDetector.main` uses RMI. |
| 7.15 | §7.3 dashboard client certificate (cf. 6.15) | The detector gets its own component certificate (`gen-certs.ps1 -AddComponent detector`, SAN `urn:eastguard:component:detector`) as its RMI client identity. | — |
