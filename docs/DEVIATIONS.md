# Deviations from the specification

Each entry records a deliberate simplification, why it was made, and what would remove it.

## Task 3 — TLS and identity

| # | Spec | Simplification | Reason / removal |
|---|------|----------------|------------------|
| 3.1 | §9.1 "protected paths for PKCS#12 files … RPC credentials" | All runtime TLS stores (token service, gateway, control plane, workloads, trust store) share one demo password (`EASTGUARD_STORE_PASS` / `keys\store.pass`). The lease signer and the CA stores have their own passwords. | One password per process role is the production setup. The demo runs every role on one machine as one user. Remove it by adding per-role `*.passwordEnv`/`*.passwordFile` settings (the config keys already exist per component). |
| 3.2 | §9.1 "Do not put secrets in … command-line arguments" | Followed. keytool reads passwords with `-storepass:env`. When no env var is set, the password lives in a git-ignored file with a current-user-only ACL. | — |
| 3.3 | §4.1 certificate revocation | No CRL/OCSP. A revoked certificate is expressed as a leaf fingerprint in `Workload.revokedCertificates` in the enforcement snapshot, and `WorkloadIdentity`/`PolicyEvaluator` check it on every connection. | Matches the spec's snapshot-based revocation; PKIX revocation checking would need a CRL distribution point the demo CA does not run. |
| 3.4 | §4.1 session resumption | TLS session resumption is left on. The identity, revocation and validity checks run on every connection against the current state, including resumed sessions, so resumption cannot bypass them. | — |
| 3.5 | `ReasonCode` | Appended `BAD_IDENTITY(18)` for "no single approved workload URI SAN / certificate outside validity", distinct from `IDENTITY_DISABLED`. | Append-only, as the enum's wire contract allows. |

## Task 4 — Token service and client

| # | Spec | Simplification | Reason / removal |
|---|------|----------------|------------------|
| 4.1 | §6.2 freshness, §9.1 "load policy from the control-plane journal" | The token service runs on a **static bootstrap snapshot** read from `bootstrap.*` keys in its properties file, and treats it as always fresh. | No control plane exists yet. Task 6 replaces the `Supplier<EnforcementView>` passed to `TokenServer` with a synced view that becomes unusable after `state.maxAgeMillis`. |
| 4.2 | §4.2 "per-client limits" | Fixed one-second window per authenticated identity (`IssueLimiter`), default 20 requests/s. The map is capped at 10 000 identities and fails closed when full. | Good enough to stop a single workload from hammering the signer. A token bucket would smooth bursts. |
| 4.3 | §1 "selected token-service denials" telemetry | Not emitted yet. Denials are logged (identity, service, reason, never the token) and counted in `TokenServer.Stats`. | Task 7 adds the UDP telemetry producer. |
| 4.4 | §4.1 / §10 "Untrusted certificate … TLS fails" | Met on the server side, which is the authoritative signal. With TLS 1.3 the **client** finishes its handshake before the server rejects its certificate, so the client sees the failure on its first read: as an `SSLException`, or on Windows often as a `SocketException` (connection reset) because the reset discards the server's alert. The demo and tests assert the server-side handshake failure and that no application reply was sent. | Inherent to TLS 1.3 client authentication. |

## Task 5 — NIO gateway

| # | Spec | Simplification | Reason / removal |
|---|------|----------------|------------------|
| 5.1 | §6.2 freshness, §9.1 "load policy from the control-plane journal" | The gateway uses the **same static bootstrap snapshot** as the token service: `bootstrap.file` in the gateway config points at the token service's properties file, and the view is always fresh. The gateway already re-reads its `Supplier<EnforcementView>` at AUTHORIZE, on `finishConnect()`, and in a 50 ms sweep that closes indexed sessions when the view stops being usable. | Task 6 passes a synced view, calls `reevaluate()` after installing a snapshot, and `closeAll(NOT_READY)` when freshness expires. |
| 5.2 | §1 "emit authenticated UDP events for gateway decisions" | Decisions go to a `DecisionSink`. Only `CountingDecisionSink` (non-blocking counters) exists. | Task 7 adds the UDP producer behind the same interface. |
| 5.3 | §4.3 deadlines | Deadlines are checked by a sweep every 50 ms over all connections (O(n), about 1,000 entries), so a timeout fires up to 50 ms late. The queued-bytes gauge in `Stats` is sampled by the same sweep. | A timer wheel would give exact deadlines; not needed at these timeouts. |
| 5.4 | §4.3 "total buffer budget" | Each connection **reserves a fixed cost** at accept: two one-record TLS buffers, plus a plaintext buffer per direction (`limits.relayBufferBytes`, at least one TLS record), about 96 KiB with the defaults. A connection is rejected when the reservation would exceed `limits.bufferBudgetBytes`. Memory is bounded by construction rather than by tracking live usage. Water marks apply to the plaintext queue in each direction (client→backend: unwrapped bytes waiting for the backend; backend→client: backend bytes plus ciphertext waiting for the client). | Reserving up front means a connection admitted under the budget can never fail later for lack of memory. Lazy or pooled buffers could raise density. |
| 5.5 | §4.3 "handshake concurrency" | `limits.maxHandshakes` counts connections in TLS_HANDSHAKE or READ_PREAMBLE. At the limit the gateway **stops accepting** (removes `OP_ACCEPT`) and new connections wait in the kernel backlog. Global and per-peer connection limits and the buffer budget **reject** (accept, then close). | Pausing accept for short-lived handshake pressure keeps legitimate clients working; hard limits still reject excess. |
| 5.6 | §4.2 step 5 "never forward early client data before admission" | The gateway reads no client bytes between a complete preamble and the flushed reply. Plaintext that arrived **in the same read as the preamble** is a protocol violation: the connection is closed with no reply and nothing reaches the backend. Bytes a client sends later while waiting (non-conforming) are read only after `ALLOW` and then relayed. | A conforming client waits for the reply (§5.1). |
| 5.7 | §5.1 replies | A malformed preamble (bad magic or version, token length outside 1..2048, trailing data) is closed **without a reply**, as the token service does for malformed requests. It is recorded as DENY/`INVALID_TOKEN`, attributed to the TLS identity when the certificate maps to a workload. A token that frames correctly but does not parse or verify gets a DENY reply. | — |
| 5.8 | §4.2 step 6, §10 "quarantine during pending backend connect" | A session closed by a command (quarantine, revocation, stale state) **while its backend connect is pending** is denied: the backend leg is cancelled, the client gets the matching status (e.g. `QUARANTINED`), and no ALLOW is sent. A **live** session is cut on both legs at once, with no reply and queued payload discarded. | — |
| 5.9 | §8 adapters, §10 "backend becomes slow" | `BackendConnector` is an adapter for the non-blocking backend connect. Tests use a double that starts `connect()` late or never, to simulate a slow network. On Windows a loopback connect to a closed port, or to a listener with a full backlog, is refused at once, so no real loopback fixture can hold a connect pending. | Production uses `BackendConnector.DIRECT`. |
| 5.10 | §9.3 "on gateway shutdown, drain only allowed sessions for a bounded interval" | `NioGateway.close()` stops accepting and **cancels all connections immediately**. | Add a draining phase (stop admissions, wait up to N seconds for RELAY sessions, then close) when an operational shutdown procedure is needed. |
| 5.11 | §4.3 "do not operate on an engine concurrently" | All delegated tasks (handshake and, rarely, data phase) run on the bounded `limits.tlsTaskThreads` executor. While a task runs, the connection has no interest ops and the selector does not touch its engine. A connection closed meanwhile is closed **without touching the engine** (no `close_notify`). If the task queue is full, the connection is closed. | — |
| 5.12 | §10 "Admission p95 under 5 ms on a warmed gateway" | `DemoM1_Nio` reports two numbers, measured by the gateway from complete preamble to flushed ALLOW. **Burst** (500 connects, 64 at a time, client crypto in the same JVM): p95 about 120 ms, mostly queueing behind other handshakes on the selector. **Warmed, sequential**: p95 about 1.1 ms on the development laptop. Neither is a load test on declared hardware. | Spec §10 load tests remain to be done (Task 10). |
| 5.13 | §6.1 decoys | One decoy listener per gateway (`decoy.listen`), served by the gateway's selector thread with no thread of its own. Accepts are bounded per wake-up, and there is no per-source rate limit on DECOY events beyond that. | The sink must drop rather than block; the Task 7 UDP queue is bounded. |
